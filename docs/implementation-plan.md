# PiForge 分阶段实施计划

当前交付止于源码分析和设计。下面是后续开发顺序和验收条件，各项数字均应实测后再写入简历。

| 阶段                    | 最小交付                                                                                                            | 如何验收                                                                                                                                                                            |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. 固定基线             | 记录 Node、依赖版本和实际构件来源。独立项目使用同一套 Pi 包。用假模型发起一次读文件，再根据结果回答。               | 完全离线；核对两次模型请求、一次工具执行、调用与结果 ID 一致、最终文本正确；另测未知工具和模型错误。参考 `packages/agent/README.md`、`packages/ai/src/providers/faux.ts`。          |
| 2. 建立可观测基线       | 用一个固定工作区和一个预定义测试构建首个编程任务；记录 run ID、模型轮数、工具错误、输入输出 Token、耗时、最终验收。 | 同一输入能重放假模型的相同事件；模型说“修好了”但断言失败时记为失败。真实模型实验另记模型版本和配置。事件依据 `packages/agent/src/types.ts`。                                        |
| 3. 工具策略、预算与取消 | 为文件工具加入工作区约束，通过公开钩子安装策略。分别限制模型请求、工具调用和总时长，超时传递到工具。                | 越界操作在写入前被拒；一轮请求多个工具时不超预算；取消后不再发下一次请求，测试子进程能收尾。对照 `packages/agent/src/agent-loop.ts`。                                               |
| 4. 上下文策略           | 实现完整日志附件、关键报错摘取与分段读取，把策略作为可替换组件。保留任务约束和成对工具消息。                        | 给相同任务提供长日志，用假模型检查实际发送的消息；可按引用找回遗漏行，压缩前后验收条件一致。对照 `packages/coding-agent/src/core/compaction/compaction.ts`。                        |
| 5. 受控恢复             | 实现追加日志、轮末检查点、未完成操作核对；记录工作区、模型、策略版本和预算。                                        | 在执行前、写入后记账前、整轮完成后三处强制中断；恢复后无重复编辑，未知副作用进入待确认。测试损坏尾条、工作区被人工修改、程序二次恢复。对照 `packages/durable/src/harness/tool.ts`。 |
| 6. 验收与有限修复       | 用任务预设的验收器运行测试，把失败断言送入下一轮，限制修复次数。                                                    | 覆盖首次成功、一次修复后成功、持续失败和取消；预算耗尽时保留最后一次失败证据；验收脚本保存在 Agent 不能修改的位置。                                                                 |
| 7. 可复现实验           | 准备修 Bug、加功能、补测试、长日志和故障恢复任务。每次从相同仓库起点启动，输出逐任务原始记录及汇总。                | 在相同模型、提示、工具权限和总预算下比较基线、只加上下文策略、只加失败反馈、两者均开启；各配置重复运行，报告成功数/总数、耗时和 Token。单独注入中断测恢复正确率与重复副作用次数。   |

## 实验口径

基线也要运行独立验收才能评分，只有“是否把失败反馈给 Agent 再修”随实验组变化。原版 Pi CLI 可另设外部参照组，同时记录其自带压缩、工具和重试配置。每次运行保留初始提交、任务定义、依赖锁、模型标识、预算和终止原因。分别统计模型请求、工具尝试、实际执行与拦截次数；可信用量缺失记为缺失。记录每题变化和成本，避免只报最好一次或把不同模型的差异归到 Harness。

## 何时扩展

首版可用单进程与本地账本。在需要跨进程调度或嵌套可恢复工具时，先用同一故障样例比较 Durable，并记录实验性接口带来的迁移成本。需要 MCP 或终端界面时，再评估上游既有模块。上游依据为 `packages/durable/README.md`、`packages/coding-agent/docs/mcp.md`、`packages/tui/package.json`。各阶段只在独立 PiForge 项目落地。
